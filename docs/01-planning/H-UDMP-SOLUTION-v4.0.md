## 0. 修订建议总览

### 0.1 对 V2/V3 的总体判断

V2 的优点是结构完整、解释充分，适合作为项目方案初稿；不足是部分标准和数据契约没有严格区分，部分技术结论直接跳到实现层。

V3 的优点是补充了 FHIR、药品、DRG/DIP、生命周期、幂等、冷热分离等关键能力；不足是压缩过度，新增模块与数据表、接口、实施阶段之间的证明链不足，容易形成“功能堆叠”。

V4 的修订原则是：保留 V2 的完整度，吸收 V3 的新增能力，用形式逻辑把“为什么要建、建什么、怎么建、如何证明建成”连接起来。

### 0.2 六类问题与修改建议

| 问题类型 | 原文表现 | 逻辑风险 | V4 修改策略 |
|---|---|---|---|
| 概念不清 | OID、FHIR、HL7 V3/R4、主数据、交换平台混用 | 标识体系、报文表达、接口协议、治理对象被放在同一层 | 单独设置“标准与概念校准”，定义每个概念所在层级 |
| 因果跳跃 | 从“数据孤岛”直接推出“建设 MDM + FHIR + 外报网关” | 缺少“痛点-原因-机制-收益-验收”的证明链 | 在执行摘要中建立一一对应矩阵 |
| 范围膨胀 | V3 一次性纳入药品、DRG/DIP、等保、FHIR、医保订阅 | 首期交付不可控，MVP 边界不清 | 按 MVP、一期、二期、三期拆分能力 |
| 标准误用 | 耗材被归入 MedicationKnowledge；API Key + JWT 被表述为双因子 | 医疗资源模型错误，安全术语不严谨 | 重写 FHIR 资源映射；将 API Key + JWT 表述为应用认证与授权上下文 |
| 指标未限定 | P99、可用性、日志留存等指标直接出现 | 不知道适用于哪些接口、哪个环境、哪个阶段 | 将指标分为 MVP 目标、生产目标、合规目标 |
| 数据模型缺口 | 字典版本、映射审核、外报任务、交换日志表不足 | 生命周期、审计、幂等无法落地 | 补充版本、审核、日志、外报、药品、诊疗项目等表 |

### 0.3 关键修改建议

1. 将“医院统一数据管理中台”定义为主数据治理、数据交换、外部报送和标准适配的组合平台，而不是单一数据库或单一接口网关。
2. 将 OID 定义为院内统一对象标识体系，将 FHIR 定义为对外资源表达和接口互操作方式，两者通过映射表和资源适配层连接。
3. 将“映射桥”提升为全平台核心机制：任何外部系统代码进入中台前，必须先转为标准主数据标识或进入待审核流程。
4. 将耗材、设备、药品、诊疗项目分别建模，避免把不同监管体系和业务语义混进同一字典。
5. 将医保代码订阅、双码并行、字典状态机和版本发布纳入正式能力，否则标准演进会继续依赖人工。
6. 将接口、表结构、状态机、唯一键、幂等键、审计日志作为“数据契约”统一描述，使后续开发不需要重新解释业务边界。
7. 将实施路线从“功能清单”改成“能力成熟度路线”：先跑通核心主数据和映射价值，再扩展外报、FHIR、DRG/DIP 和高级治理。

## 1. 形式逻辑框架

### 1.1 核心命题

H-UDMP 的核心命题是：

> 如果医院的基础数据由多个业务系统各自定义，且系统之间通过点对点接口直接交换，那么数据一致性、系统可替换性、外部报送效率和运营分析可信度都会受制于最弱的接口与最混乱的字典；因此，医院需要一个统一的主数据管理与交换治理平台，把“实体定义、编码映射、数据分发、版本演进、审计追溯”集中治理。

这个命题包含四个必要条件：

| 必要条件 | 含义 | 缺失后果 |
|---|---|---|
| 统一实体定义 | 同一科室、人员、耗材、设备、药品、诊疗项目在全院有唯一标准身份 | 报表口径不一致 |
| 标准编码映射 | 外部系统编码可稳定映射到中台标准编码 | 换系统就重写接口 |
| 可追溯交换链路 | 每次数据进入、清洗、转换、分发都有日志 | 故障不可定位，审计不可证明 |
| 可演进版本机制 | 字典和标准更新可发布、灰度、回滚、追溯 | 医保码、药品目录、诊疗项目更新依赖人工 |

### 1.2 逻辑链条

```text
业务痛点
  ↓
根因识别：多源字典、点对点接口、缺少统一版本、缺少审计链
  ↓
机制设计：主数据、映射桥、交换网关、生命周期、外报网关
  ↓
数据契约：统一标识、状态机、幂等键、版本号、审计日志
  ↓
实施路径：MVP验证 → 一期固化 → 二期扩展 → 三期运营
  ↓
验收证据：一致性、可用性、时延、对账效率、报送成功率、追溯能力
```

### 1.3 边界原则

H-UDMP 不替代 HIS、LIS、EMR、SPD、资产系统等业务系统，不承载临床业务闭环；它负责全院共享数据的统一定义、映射、交换、分发、外报和治理。

H-UDMP 不直接“创造”国家标准编码；它接收、订阅、导入、校验和发布来自国家医保局、国家药监局、卫健委标准和院内治理委员会确认的编码版本。

H-UDMP 不把所有数据都复制为数据仓库；它优先治理高频、跨系统、影响报表和外报的主数据，分析型宽表和指标建模可作为后续数据资产层扩展。

## 2. 执行摘要

### 2.1 平台定位

H-UDMP（医院统一数据管理中台）定位为全院数据的“法典、翻译层、路由器和审计链”。

- “法典”：定义全院统一主数据，包括科室、人员、耗材、设备、药品、诊疗项目等。
- “翻译层”：通过映射桥把 HIS、SPD、LIS、EMR、资产系统等外部编码翻译为中台标准标识。
- “路由器”：以 REST、FHIR、Webhook、批量导入导出等方式进行标准数据分发。
- “审计链”：记录每次数据接入、清洗、映射、发布、外报和人工审核行为。

### 2.2 痛点、机制与验收指标

| 痛点 | 根因 | 中台机制 | 预期收益 | 验收指标 |
|---|---|---|---|---|
| 数据孤岛 | 多系统各自维护字典 | 主数据中心 + 映射桥 | 报表口径统一 | 核心字典重复率趋近 0；映射准确率 ≥ 95% |
| 厂商锁定 | 点对点接口直接绑定外部代码 | 标准 API + 映射桥 | 换系统不改内部报表 | 更换外部系统时只调整映射和适配器 |
| 上报困难 | 报送口径分散在各系统 | 外报网关 + 模板版本 | 报送数据可追溯、可复用 | 报送任务成功率 ≥ 99%；失败可重试 |
| 医保对账低效 | 耗材、药品、项目编码不一致 | 医保代码订阅 + 双码并行 | 降低人工核对 | 月结对账差异可定位到明细 |
| 标准演进滞后 | 字典缺少生命周期 | Blueprint 版本发布 | 支持灰度、回滚、追溯 | 任一字典可 AS OF 查询 |
| 故障不可定位 | 缺少交换日志和幂等机制 | 交换日志 + DLQ + SAGA 补偿 | 降低重复写入和数据丢失 | `source_system + source_tx_id` 幂等有效 |

### 2.3 建设策略

H-UDMP 采用“主数据治理 + 数据交换治理 + 标准适配 + 外报出口”的组合架构。首期不追求一次性替代所有接口，而是以耗材 27 位码、科室字典和 SPD 接入为 MVP，证明统一字典和映射桥的业务价值；后续逐步扩展药品、设备、诊疗项目、FHIR、DRG/DIP 和外报任务。

## 3. 项目概述

### 3.1 项目背景

医院信息化长期呈现“烟囱式”架构：

- HIS、SPD、LIS、EMR、资产系统、设备系统分别维护自己的基础字典。
- 同一实体在不同系统中的名称和编码不一致，例如“心外科”“心脏外科”“胸心外科”可能指向同一组织单元。
- 点对点接口直接绑定外部系统字段，任一系统升级或更换都会牵动下游报表、接口和外报程序。
- 医保结算、互联互通测评、电子病历评级、DRG/DIP 支付改革对编码一致性、过程可追溯性和数据质量提出更高要求。

### 3.2 建设目标

| 目标维度 | 目标定义 | 落地方式 |
|---|---|---|
| 标准化 | 全院核心实体使用统一编码、统一名称、统一状态 | MDM 主数据中心、OID、标准字典 |
| 解耦合 | 外部系统变化不直接影响内部模型和报表 | 映射桥、适配器、标准 API |
| 原子化 | 规格、剂量、单位、包装、型号等字段拆至可统计粒度 | 清洗流水线、字典字段约束 |
| 可观测 | 接口健康、交换链路、异常数据可监控 | 交换日志、API 注册表、Prometheus/Grafana |
| 可演进 | 国家标准、医保码、药品目录变更可版本化发布 | 字典生命周期、Blueprint、双码并行 |
| 合规化 | 支撑互联互通、等保、隐私保护、医保外报 | 审计、脱敏、权限、外报网关 |

### 3.3 适用范围

| 范围类别 | 纳入范围 | 暂不纳入或后续扩展 |
|---|---|---|
| 系统 | HIS、SPD、LIS、EMR、资产系统、设备系统、医保上报系统 | 影像原始文件归档、科研数据湖、互联网医院业务闭环 |
| 主数据 | 科室、人员、耗材、设备、药品、诊疗项目 | 病历全文、检验原始曲线、影像 DICOM 原始数据 |
| 流程 | 数据接入、清洗、映射、分发、外报、审计 | 临床医嘱开立、药房发药、收费结算主流程 |
| 标准 | WS/T 671、FHIR R4、OID、UDI、医保编码、ICD、DRG/DIP | 未经院内确认的数据标准草案 |

### 3.4 干系人

| 干系人 | 核心诉求 | 中台响应 |
|---|---|---|
| 信息部门 | 降低接口耦合，提升故障定位能力 | API 注册、交换日志、监控告警 |
| 数据治理员 | 字典准确、映射可审核、版本可追溯 | 审核任务、状态机、版本快照 |
| 临床科室 | 系统间数据一致，不增加操作负担 | 标准字典分发、无感新增流程 |
| 医保办 | 对账、外报、医保目录更新自动化 | 医保代码订阅、外报网关、对账引擎 |
| 财务科 | 成本归集准确，材料和项目口径稳定 | 耗材、药品、诊疗项目标准化 |
| 院领导 | 运营数据准确及时 | 统一口径报表、数据质量报告 |
| 厂商 | 接口标准清晰，对接成本可控 | 开发者门户、沙箱、OpenAPI/FHIR 文档 |

### 3.5 能力边界

H-UDMP 是全院共享数据与交换治理平台，不替代各业务系统的业务状态机。例如，SPD 仍负责采购、库存和出入库业务；H-UDMP 负责耗材标准字典、医保码映射、编码订阅、对账口径和数据分发。

## 4. 标准与概念校准

### 4.1 术语表

| 术语 | 全称 | 本文定义 |
|---|---|---|
| MDM | Master Data Management | 主数据管理，全院共享实体的统一定义、编码、状态和版本治理 |
| OID | Object Identifier | 对象标识符，用于院内统一标识命名空间和外部标准标识承接 |
| FHIR | Fast Healthcare Interoperability Resources | HL7 医疗互操作资源标准，本文以 R4 作为对外接口基线，关注 R5 演进 |
| WS/T 671 | 医院信息互联互通标准化成熟度测评方案 | 互联互通测评相关标准要求，指导医院信息平台建设与评价 |
| UDI | Unique Device Identifier | 医疗器械唯一标识，用于器械和耗材的监管追溯 |
| NHSA | National Healthcare Security Administration | 国家医保局，医保药品、耗材、诊疗项目等编码管理的重要来源 |
| DRG | Diagnosis Related Groups | 疾病诊断相关分组，用于医保支付和绩效分析 |
| DIP | Diagnosis-Intervention Packet | 病种分值付费，用于医保支付管理 |
| SAGA | - | 分布式事务补偿模式，用于跨系统交换失败后的补偿处理 |
| DLQ | Dead Letter Queue | 死信队列，用于保存多次重试后仍失败的交换任务 |
| RTO | Recovery Time Objective | 恢复时间目标 |
| RPO | Recovery Point Objective | 恢复点目标 |

### 4.2 OID 与 FHIR 的关系

OID 和 FHIR 不是同一层概念：

- OID 解决“对象如何被唯一标识”的问题。
- FHIR 解决“对象如何以标准资源形式被表达和交换”的问题。
- H-UDMP 内部可用 OID、UUID、医保码、UDI、ICD 等多种标识共存，但必须在主数据表和映射表中明确其作用域。
- H-UDMP 对外通过 FHIR API 暴露资源时，应把内部标识放入 FHIR `identifier`，把院内扩展属性放入 `extension` 或院内 Profile。

### 4.3 FHIR 资源映射校准

| 主数据对象 | 推荐 FHIR 表达 | 说明 |
|---|---|---|
| 科室/院区/组织 | Organization、Location | Organization 表示组织单元，Location 表示物理位置 |
| 人员 | Practitioner、PractitionerRole | 区分人员身份和在某机构中的角色 |
| 设备 | DeviceDefinition、Device | 区分设备规格定义和单台设备实例 |
| 药品 | Medication、MedicationKnowledge | 药品知识和药品实体可按场景选择 |
| 耗材 | Device、DeviceDefinition、SupplyDelivery 或院内 Profile | 耗材不应简单归入 MedicationKnowledge |
| 诊疗项目 | ChargeItemDefinition、ActivityDefinition 或院内 Profile | 需结合医院接口场景与本地 Profile 设计 |

本文采用 FHIR R4 作为医院对接基线，原因是国内外医疗互操作生态中 R4 支持更广；同时记录 HL7 官网 current release 为 R5，后续版本升级应通过适配层完成，不直接冲击内部主数据模型。

### 4.4 医保 27 位码与 UDI

医保 27 位码用于医保医用耗材分类、支付和对账；UDI 用于医疗器械唯一标识和监管追溯。两者都可用于耗材和器械治理，但语义不同：

- 医保码偏支付、目录和医保结算。
- UDI 偏产品识别、监管追溯和供应链。
- H-UDMP 应建立医保码、UDI、注册证号、院内耗材编码之间的关联关系。
- 对 27 位码的校验不得编造未确认算法。系统应优先使用国家医保局发布的全量字典、增量通知和字段规则进行比对；如存在权威校验位规则，再在校验服务中固化。

### 4.5 安全概念校准

API Key + JWT 不应表述为“双因子认证”。本文将其定义为：

- API Key/Secret：第三方应用身份认证。
- JWT：用户会话、服务授权上下文或短期访问令牌。
- RBAC/ABAC：按角色、系统、接口、数据范围授权。
- TLS、字段脱敏、审计日志、备份加密：分别属于传输安全、数据最小化、行为追溯和存储/归档安全。

## 5. 总体架构

### 5.1 架构模式

H-UDMP 采用“集成平台 + 数据中台 + 标准适配层”三面架构：

| 架构面 | 职责 | 关键能力 |
|---|---|---|
| 集成平台面 | 接口管理、协议适配、报文转发、重试补偿 | REST、Webhook、批量导入、交换日志 |
| 数据中台面 | 主数据定义、映射、清洗、生命周期、版本发布 | MDM、映射桥、字典状态机、Blueprint |

### 6.2 主数据管理中心

#### 6.2.1 组织机构与人员

组织机构用于统一院区、科室、病区、诊疗组、虚拟科室等对象。

功能要求：

- 支持院区、科室、病区、诊疗组的层级结构。
- 支持标准名称、简称、别名、拼音码和历史名称检索。
- 支持科室合并、拆分、停用后的历史追溯。
- 支持人员执业资质、多点执业、岗位角色、科室任职关系。
- 支持外部系统科室 ID、人员 ID 与中台标准标识的映射。

关键规则：

- 组织机构主数据必须有唯一 `dept_id`、标准编码、标准名称、状态、版本号。
- 人员身份与人员任职角色分开建模，避免一个人在多个科室任职时复制人员档案。

#### 6.2.2 耗材 27 位码库

耗材字典以医保 27 位码、注册证号、UDI、院内耗材编码等标识共同描述耗材规格。

功能要求：

- 支持医保耗材全量库导入、增量更新和差分比对。
- 支持 27 位码、20 位分类码、注册证号、UDI、通用名、品牌、规格型号检索。
- 支持规格值、规格单位、包装单位、材质、型号、注册证号等原子化字段。
- 支持医保码变更后的双码并行：旧码 `DEPRECATED`，新码 `ACTIVE`，保留替代关系。
- 支持耗材使用、出库、收费和医保对账的编码口径统一。

关键规则：

- 严禁只用一个 `spec` 字段保存“50ml*10支/盒”这类复合字符串。
- 对 27 位码的合法性验证以权威字典、长度、字符类型、分类层级和国家发布规则为准，不在本文固化未经确认的校验位算法。

#### 6.2.3 设备/器械分类参考字典

设备/器械分类在 H-UDMP 中仅作为标准分类、注册备案、UDI 和外部设备系统对接的参考字典，不承载设备资产全生命周期管理。

功能要求：

- 保存医疗器械分类目录中的一级/二级产品类别、产品描述、预期用途、品名举例、管理类别。
- 支持注册备案号、UDI、医保耗材码与器械分类参考关系的查询和对照。
- 为医用设备全生命周期管理系统、资产系统、SPD 或监管报送提供标准分类参考。
- 通过映射桥记录外部设备系统分类编码与中台参考分类的对应关系。

关键规则：

- H-UDMP 不管理资产条码、出厂序列号、所在科室、采购日期、维保、维修、报废、盘点等资产实例流程。
- 设备状态流转属于医用设备全生命周期管理系统；H-UDMP 只提供分类字典、标准编码和跨系统映射支撑。
- 若外部设备系统需要引用 H-UDMP 分类，应通过标准分类 ID 或映射桥完成，不把设备业务状态写回 H-UDMP。

#### 6.2.4 药品字典

药品字典用于统一药品基础信息、包装层级、医保目录关系和特殊药品标识。

功能要求：

- 支持批准文号、生产企业、通用名、商品名、剂型、规格、ATC 编码等基础字段。
- 支持大包装、中包装、最小制剂单位之间的换算关系。
- 支持医保药品目录、集采标记、基药标记、抗菌药物分级、麻精毒放标识。
- 支持院内药品编码、医保药品编码、药监数据之间的映射。

关键规则：

- 药品“基础品种”和“包装规格”分开建模。
- 医保目录关系应作为独立关系表维护，避免医保属性变化时反复改动药品基础表。

#### 6.2.5 诊疗项目字典

诊疗项目字典用于统一收费项目、检验检查项目、手术操作、治疗项目和 DRG/DIP 关联口径。

功能要求：

- 支持院内项目编码、医保项目编码、项目名称、项目类别、价格、医保支付标准。
- 支持 ICD-9-CM-3 手术操作编码、ICD-10 诊断关联、手术分级。
- 支持检验、检查、治疗、手术、护理等项目分类。
- 支持 DRG/DIP 分组器接口所需字段的标准化输出。

关键规则：

- 诊疗项目字典不直接替代收费系统，但应成为收费、医保、病案、绩效分析之间的统一口径。

### 6.3 异构系统映射桥

映射桥是 H-UDMP 的核心解耦机制。

#### 6.3.1 映射对象

| 映射类别 | 来源示例 | 目标 |
|---|---|---|
| 科室 | HIS 科室 ID、LIS 科室代码、资产系统科室名称 | 标准科室 master_id/OID |
| 人员 | HIS 工号、EMR 医师 ID、CA 证书标识 | 标准人员 master_id/OID |
| 耗材 | SPD 耗材编码、供应商编码、医保码、UDI | 标准耗材规格 id |
| 设备 | 资产系统规格 ID、设备系统型号 | 标准设备规格 id |
| 药品 | HIS 药品编码、药房编码、医保药品码 | 标准药品/包装 id |
| 诊疗项目 | 收费项目码、医保项目码、手术操作码 | 标准诊疗项目 id |

#### 6.3.2 映射规则

- 支持精确匹配、别名匹配、拼音匹配、模糊匹配和人工确认。
- 自动匹配结果必须有置信度，低于阈值的进入待审核。
- 多个外部系统代码可以映射到同一标准主数据。
- 同一 `source_system + source_key + category` 不得同时指向多个有效目标。
- 映射变更必须记录审核人、审核时间、变更原因和生效版本。

#### 6.3.3 映射补全工作流

```text
外部系统推送非标数据
  ↓
映射桥检索
  ├─ 命中 ACTIVE 映射：返回标准标识
  ├─ 命中 DEPRECATED 映射：返回替代建议并记录告警
  └─ 未命中：创建 PENDING 审核任务
          ↓
     数据治理员审核
          ↓
     选择已有主数据 / 新增主数据 / 拒绝
          ↓
     生成映射记录并进入版本发布
```

### 6.4 数据交换与清洗引擎

#### 6.4.1 统一接入

接入方式：

- REST API：业务系统实时推送。
- FHIR API：标准资源读写。
- Webhook：订阅系统回调。
- 批量导入：CSV、Excel、JSON、XML。
- 定时抓取：对不支持推送的系统读取视图、接口或文件。

#### 6.4.2 清洗流水线

| 步骤 | 处理逻辑 | 示例 |
|---|---|---|
| 格式归一化 | 将 JSON、XML、CSV 转为内部标准对象 | `dept` → `dept_name` |
| 字段标准化 | 去空格、全半角转换、大小写归一、日期格式归一 | `２０２６/５/４` → `2026-05-04` |
| 原子化拆分 | 拆分规格、单位、包装、剂量 | `22mm` → `value=22, unit=mm` |
| 语义校验 | 核对必填、状态、编码层级、字典存在性 | 科室不存在 → 待审核 |
| 映射转换 | 外部编码转换为标准主数据标识 | HIS 科室 ID → 标准科室 id |
| 异常处理 | 重试、补偿、DLQ、人工处理 | 多次失败进入死信队列 |

#### 6.4.3 交接保障

每笔交换必须有：

- `source_system`：来源系统。
- `source_tx_id`：来源事务号。
- `payload_hash`：报文摘要。
- `idempotency_key`：幂等键，建议由 `source_system + source_tx_id` 构成。
- `exchange_status`：SUCCESS、FAILED、RETRY、DLQ。
- `retry_count`：重试次数。
- `trace_id`：链路追踪标识。

### 6.5 字典生命周期与版本发布

#### 6.5.1 状态机

```text
DRAFT → ACTIVE → DEPRECATED → RETIRED
  ↑        ↓           ↓
  └── 回退草案     替代关系/停用说明
```

状态含义：

- DRAFT：草案，可编辑，不对业务系统正式分发。
- ACTIVE：当前有效，可被查询、映射、分发和外报。
- DEPRECATED：不建议新增使用，但历史数据仍可解释。
- RETIRED：退休，仅用于历史追溯和审计。

#### 6.5.2 Blueprint 发布

每次字典发布形成一个 Blueprint：

- 命名规则：`vYYYYMMDD-N`。
- 内容：字典类型、变更明细、影响范围、回滚点、审批记录。
- 发布方式：全量发布、差分发布、灰度发布。
- 查询能力：支持按当前版本查询，也支持 `AS OF` 历史时点查询。

### 6.6 医保代码订阅与双码并行

医保代码订阅用于跟踪国家医保局编码变更。

订阅方式：

- Pull：定期轮询官方编码平台或院内下载目录。
- Push：接收上级平台或厂商推送。
- Manual：人工上传官方文件。

变更处理：

| 变更类型 | 处理方式 |
|---|---|
| 新增 | 导入为 DRAFT，审核后 ACTIVE |
| 修改 | 生成差分，保留旧值历史 |
| 停用 | 旧码设为 DEPRECATED 或 RETIRED |
| 替代 | 建立 old_code → new_code 替代关系 |

双码并行策略：

- 新标准发布后，旧码不立即删除。
- 报表和外报按任务版本选择代码口径。
- 业务系统未完成切换时，映射桥可透明转换。
- 超过院内规定过渡期后，停止旧码新增使用。

### 6.7 FHIR R4 API

FHIR API 面向需要标准医疗资源交换的系统，不强制替代院内 REST API。

能力要求：

- 提供 Organization、Location、Practitioner、Device、DeviceDefinition、Medication、MedicationKnowledge 等资源读接口。
- 对暂不适合原生 FHIR 资源表达的耗材、诊疗项目，采用院内 Profile 或扩展字段。
- 错误返回 OperationOutcome。
- 内部字段不直接暴露数据库结构，通过资源适配层生成。

### 6.8 外报数据出口网关

外报网关统一管理医保、卫健委、等级评审、院内专项上报任务。

功能要求：

- 外报模板版本管理。
- 数据提取、预校验、预脱敏、格式转换。
- 数据水印和批次号。
- 断点续传、指数退避、失败重试。
- 外报任务审计，保留报送人、报送时间、数据范围、模板版本、响应结果。

## 7. 核心功能模块设计

### 7.1 耗材字典服务

#### 7.1.1 数据模型原子化

| 字段 | 说明 | 规则 |
|---|---|---|
| `material_id` | UUID 主键 | 中台内部主键 |
| `yb_code_27` | 医保 27 位码 | 唯一，可为空但需说明原因 |
| `yb_code_20` | 医保 20 位分类码 | 从权威字典或规则提取 |
| `udi_di` | UDI-DI | 与国家药监局 UDI 数据库关联 |
| `reg_number` | 注册证号 | 支持国产、进口、备案凭证 |
| `generic_name` | 医保通用名 | 标准名称 |
| `brand_name` | 品牌/生产企业 | 标准化维护 |
| `material_attr` | 材质 | 独立字段或枚举 |
| `spec_value` | 规格值 | 不含单位 |
| `spec_unit` | 规格单位 | 如 mm、ml、mg |
| `model_detail` | 型号 | 保持原始型号但去除明显噪声 |
| `unit_pkg` | 包装单位 | 盒、个、套、支 |
| `status` | 生命周期状态 | DRAFT/ACTIVE/DEPRECATED/RETIRED |
| `version_id` | 发布版本 | 指向 Blueprint |

#### 7.1.2 入库与增项流程

```text
扫码/输入医保码或 UDI
  ↓
查询中台耗材字典
  ├─ 匹配成功：带出通用名、品牌、规格、注册证号
  └─ 匹配失败：进入标准增项流程
          ↓
     检索医保全量库/UDI库/注册证信息
          ↓
     自动填充候选字段
          ↓
     数据治理员审核
          ↓
     发布为 ACTIVE 后供 SPD/HIS 使用
```

#### 7.1.3 支撑场景

- 医保对账：出库、收费、医保结算使用同一耗材编码关系。
- 损耗分析：按材质、规格、科室、手术类型统计耗材损耗。
- 效期预警：按规格型号和批次进行库存调拨建议。
- 集采用量统计：按集采批次、企业、医保码汇总用量。

### 7.2 设备/器械分类参考服务

设备/器械分类参考服务用于沉淀医疗器械分类目录、UDI 关联、注册备案号和外部设备系统分类映射。它不是医用设备全生命周期管理系统。

| 对象 | 内容 | 示例 |
|---|---|---|
| 分类参考 | 一级/二级产品类别、产品描述、预期用途、品名举例、管理类别 | 07 医用诊察和监护器械 |
| 标识对照 | UDI、注册备案号、医保耗材码、外部设备系统分类编码 | UDI-DI、国械注准号、外部分类码 |

不纳入 H-UDMP 的设备生命周期功能：

```text
资产建档 → 入库 → 调拨 → 在用 → 维修 → 计量/保养 → 停用 → 报废
```

上述流程应由医用设备全生命周期管理系统负责。H-UDMP 与该系统的关系是：

```text
H-UDMP 提供标准分类/编码/映射
  ↓
医用设备全生命周期管理系统引用这些标准
  ↓
资产实例、状态流转、采购维保和报废流程在外部系统闭环
```

### 7.3 药品字典服务

#### 7.3.1 三层模型

| 层级 | 表 | 职责 |
|---|---|---|
| 药品基础 | `dict_drug_base` | 通用名、批准文号、生产企业、剂型、特殊药品标识 |
| 包装层级 | `dict_drug_package` | 大包装、中包装、最小单位、换算比例 |
| 医保关系 | `dict_drug_insurance_relation` | 医保编码、医保目录、支付类别、集采状态 |

#### 7.3.2 支撑场景

- 合理用药审查：统一药品身份、剂型、规格。
- 医保审核：医保编码和院内药品编码一致。
- 集采执行：统计集采药品使用量和替代情况。
- 财务核算：不同包装单位可换算到最小制剂单位。

### 7.4 诊疗项目与 DRG/DIP 支撑

诊疗项目字典为收费、病案、医保支付和绩效分析提供统一项目口径。

关键字段：

- 项目编码、项目名称、项目类别。
- 医保项目编码、医保支付类别。
- ICD-9-CM-3 手术操作编码。
- 手术分级、计价单位、收费价格。
- DRG/DIP 分组器所需的诊断、手术、治疗项目映射。

DRG/DIP 接口流程：

```text
病案首页/结算明细
  ↓
诊断编码 + 手术操作编码 + 诊疗项目标准化
  ↓
调用分组器
  ↓
返回 DRG/DIP 分组、权重、分值、异常提示
  ↓
保存分组结果与输入版本
```

### 7.5 跨系统无感新增

当业务系统需要新增规格、科室、项目时，不应让用户重复进入多个系统维护。

```text
业务系统搜索标准字典
  ↓ 未找到
业务系统进入“新标准项申请”
  ↓
调用 H-UDMP 创建 DRAFT
  ↓
数据治理员审核
  ↓
发布 ACTIVE
  ↓
业务系统收到回调并完成本地引用
```

### 7.6 业财对账引擎

业财对账以“业务发生明细 + 标准编码 + 财务结算口径”为核心。

```text
SPD 出库明细 / HIS 收费明细 / 医保结算明细
  ↓
映射到耗材、药品、诊疗项目标准编码
  ↓
按医保目录、集采批次、科室、供应商汇总
  ↓
与月结报告或医保反馈文件比对
  ↓
自动确认 / 系统标注差异 / 人工介入
```

### 8.3 映射解析请求

```json
{
  "source_system": "HIS",
  "category": "department",
  "source_key": "HIS_DEPT_001",
  "source_desc": "心外科",
  "source_tx_id": "HIS-20260504-000001"
```

### 8.4 映射解析响应

匹配成功：

```json
{
  "status": "MATCHED",
  "target_master_id": "8b2f7f67-0000-4000-9000-000000000001",
  "target_oid": "1.2.156.xxxxx.1.2.001",
  "confidence": 1.0,
  "mapping_status": "ACTIVE"
}
```

待审核：

```json
{
  "status": "PENDING_REVIEW",
  "review_task_id": "task-20260504-0001",
  "candidate_count": 2,
  "message": "未找到可自动生效的映射，请等待数据治理员审核"
}
```

### 8.5 幂等契约

所有写入型交换接口必须满足：

- 同一 `source_system + source_tx_id` 重复提交时，不产生重复业务记录。
- 若报文摘要一致，返回首次处理结果。
- 若报文摘要不一致，返回冲突错误并进入审计日志。
- 幂等键保留期限不得短于业务系统可能重试的最大时间窗口。

### 8.6 错误码

| 错误码 | 含义 | 处理建议 |
|---|---|---|
| `MAPPING_NOT_FOUND` | 未找到映射 | 创建审核任务 |
| `MAPPING_CONFLICT` | 映射冲突 | 人工处理 |
| `CODE_DEPRECATED` | 编码已废弃 | 返回替代编码 |
| `IDEMPOTENCY_CONFLICT` | 幂等键重复但报文不同 | 拒绝写入并审计 |
| `VALIDATION_FAILED` | 字段校验失败 | 返回字段明细 |
| `EXPORT_TEMPLATE_INVALID` | 外报模板无效 | 停止任务 |
| `FHIR_OPERATION_OUTCOME` | FHIR 资源错误 | 返回 OperationOutcome |

## 9. 数据库设计

### 9.1 设计原则

- 所有核心字典表必须包含主键、标准编码、标准名称、状态、版本、创建时间、更新时间。
- 所有外部编码不得直接作为内部逻辑主键，必须通过映射桥转换。
- 历史数据必须可解释，因此字典停用后不能物理删除。

## 10. 治理、运维与安全

### 10.1 组织角色

| 角色 | 职责 |
|---|---|
| 平台管理员 | 系统运维、权限分配、接口注册、监控告警 |
| 数据治理员 | 字典维护、映射审核、版本发布、质量检查 |
| 开发者 | 适配器开发、接口对接、沙箱测试 |
| 审计员 | 操作审计、外报审计、合规检查 |
| 业务联络员 | 科室、医保办、财务等业务口径确认 |

### 10.2 运维规范

- 映射、字典、外报模板变更必须走审批流程。
- 生产发布必须生成版本号、变更摘要和回滚点。
- 接口连续失败、时延超阈值、队列积压、DLQ 增长必须告警。
- 每日全量备份，关键数据库启用 WAL 归档。
- 每季度至少一次恢复演练，并记录恢复耗时。

### 10.3 安全策略

| 安全层 | 策略 |
|---|---|
| 传输安全 | HTTPS/TLS，内网服务间可使用 mTLS |

## 11. 实施路线图

### 11.1 MVP：10-12 周

目标：证明统一字典和映射桥价值。

交付内容：

- FastAPI + PostgreSQL + Redis 基础环境。
- 科室字典、耗材 27 位码字典基础模型。
- 耗材导入、检索、基础清洗。
- 映射桥基础 API：科室和耗材映射解析。
- 接入 1 个业务系统，建议 SPD。
- 基础交换日志和错误记录。

验收标准：

- 耗材字典可导入、检索、分发。
- 科室字典可映射到至少 1 个外部系统。
- 未匹配项可进入待审核。
- 重复提交不会产生重复记录。

### 11.2 一期：主数据与交换治理，3-4 个月

目标：形成可生产运行的主数据和交换治理能力。

交付内容：

- 扩展组织机构、人员、耗材、设备/器械分类参考字典。
- 映射审核工作流和管理界面。
- API 注册表、开发者门户、OpenAPI 文档。
- Celery 清洗队列、重试、DLQ。
- Prometheus/Grafana 基础监控。
- 字典状态机和 Blueprint 发布。

验收标准：

- 核心字典支持 DRAFT/ACTIVE/DEPRECATED/RETIRED。
- 核心接口可观测，错误可追踪到交换日志。
- 映射变更可审计、可回滚。

### 11.3 二期：药品、诊疗项目、医保订阅与外报，4-6 个月

目标：扩大标准化对象范围，支撑医保对账和外部报送。

交付内容：

- 药品字典三层模型。
- 诊疗项目字典和 ICD/医保项目关系。
- 医保代码订阅、差分比对、双码并行。
- 业财对账引擎。
- 外报模板、外报任务、断点续传、数据水印。
- 外报审计和报送结果回写。

验收标准：

- 医保代码变更可生成差异报告。
- 药品和诊疗项目可参与对账。
- 外报任务可重试、可追溯、可复核。

### 11.4 三期：FHIR、DRG/DIP 与高级治理，6 个月+

目标：增强互操作能力和数据治理成熟度。

交付内容：

- FHIR R4 资源适配层。
- DRG/DIP 分组器接口和结果归档。
- 数据质量评分、映射准确率月报。
- 冷热分离、归档查询、长期审计。
- 更完整的灾备演练和等保整改闭环。

验收标准：

- FHIR 资源可按院内 Profile 输出。
- DRG/DIP 输入版本、分组结果、异常提示可追溯。
- 数据质量指标进入常态化运营。

## 14. 附录

### 14.1 开发提示词合集

#### A.1 初始化项目骨架

请基于 FastAPI、SQLAlchemy 2.0、PostgreSQL 16、Redis 7 创建 H-UDMP 项目骨架。目录包含 `app/api/`、`app/models/`、`app/schemas/`、`app/services/`、`app/core/`、`app/tasks/`、`migrations/`、`tests/`、`docker/`。实现统一时间戳、软删除、状态字段、版本字段和基础健康检查。

#### A.2 主数据模型

实现科室、人员、耗材、设备、药品、诊疗项目模型。所有模型必须包含内部 UUID、标准编码、标准名称、状态、版本号、创建时间、更新时间。外部系统编码不得直接作为内部主键。

#### A.3 映射桥

实现 `sys_mapping_bridge` 和 `sys_mapping_review_task`。提供 `/api/v1/mapping/resolve` 接口：命中返回标准主数据 ID；未命中创建待审核任务；冲突返回 `MAPPING_CONFLICT`。映射变更必须记录审核人、审核时间、变更原因和版本。

#### A.4 批量导入与清洗

实现 CSV/Excel 导入，支持 UTF-8、GBK 编码识别，流式读取，失败明细导出。耗材规格必须拆分规格值和规格单位，不得只保存复合规格字符串。

#### A.5 字典生命周期

实现 `DRAFT → ACTIVE → DEPRECATED → RETIRED` 状态机和 `sys_code_version` 发布表。发布版本命名为 `vYYYYMMDD-N`，支持差分发布、回滚和 AS OF 查询。

#### A.6 交换日志与幂等

实现 `sys_exchange_log`，所有写入型接口使用 `source_system + source_tx_id` 幂等键。重复报文返回首次处理结果；同幂等键但报文摘要不同返回冲突错误。

#### A.7 FHIR R4 适配

实现 FHIR R4 读接口，将科室映射到 Organization/Location，人员映射到 Practitioner/PractitionerRole，设备映射到 Device/DeviceDefinition，药品映射到 Medication/MedicationKnowledge。耗材和诊疗项目按院内 Profile 或扩展字段表达。错误返回 OperationOutcome。

#### A.8 外报网关

实现外报模板、外报任务、数据提取、预脱敏、数据水印、断点续传、指数退避、失败重试和外报审计。外报任务必须记录模板版本、字典版本、数据范围、报送人和响应结果。
