# 主数据驱动的人员全生命周期统一身份与权限管理方案

> **状态**：迭代目标（非当前实现）
> **版本**：v0.2
> **日期**：2026-06-04
> **提出人**：项目负责人

---

## 1. 核心理念

> **系统权限不是分配给一个人的，而是这个人自带的属性。**
> 一个人从入职起，他的岗位、科室、职称就决定了他能用什么系统、能做什么事。
> 离职时，状态变为"离职"，所有系统同步失效——不需要逐个去回收权限。

**当前系统的做法（错误）**：

```text
建一个用户 → 指定角色 → 分配系统权限
（权限是"额外加上的"）
```

**主数据驱动的做法（正确）**：

```text
建一个人 → 填写岗位/科室/人员类型 →
    系统自动推导：此人可登录哪些系统、在每个系统中是什么角色
（权限是"人固有的"，由岗位规则自动决定）
```

## 3. 数据模型：权限是 DictPerson 的固有属性

### 3.1 DictPerson 扩展

现有 `dict_persons` 表已包含核心字段，在此基础上直接增加系统访问属性：

| 字段 | 类型 | 说明 |
|------|------|------|
| `person_id` | UUID PK | 人员主数据唯一标识 |
| `person_code` | VARCHAR | 工号/人员编码 |
| `person_name` | VARCHAR | 姓名 |
| `department_id` | UUID FK→部门 | **决定部门级权限** |
| `position` | VARCHAR | 岗位（主任医师/工程师/护士...）—— **决定角色** |
| `person_type` | VARCHAR | 本院职工/规培生/进修生/供应商...—— **决定系统访问范围** |
| `status` | VARCHAR | ACTIVE / INACTIVE / RESIGNED / RETIRED —— **决定能否登录** |
| `phone` / `email` | | 联系方式，用于找回密码等 |

> **关键变更**：不再新增 `platform_account`、不再新增 `person_system_role` 等"分配"表。
> 系统访问规则通过**配置层**表达，不属于人员主数据本身。

### 3.2 访问规则配置（H-UMDG 系统配置，非人员属性）

在 H-UMDG 中维护一组**规则配置**，描述"什么样的人有什么权限"：

```yaml
# 规则配置示例（存储在 system_config 表或配置文件中）
access_rules:
  # 规则：设备科工程师 → 可访问 H-MELC，角色为 ENGINEER
  - system_code: H-MELC
    match:
      position: "工程师"
      department: "设备科"
    roles: ["ENGINEER", "DEPT_USER"]

  # 规则：设备科科长 → 可访问 H-MELC，角色为 DEVICE_ADMIN
  - system_code: H-MELC
    match:
      position: "科长"
      department: "设备科"
    roles: ["DEVICE_ADMIN", "SYS_ADMIN"]

  # 规则：护士 → 可访问 H-MELC，角色为 DEPT_USER（仅扫码报修）
  - system_code: H-MELC
    match:
      person_type: "本院职工"
      position: "护士"
    roles: ["DEPT_USER"]

  # 规则：供应商人员 → 仅可访问供应商门户
  - system_code: H-MELC
    match:
      person_type: "供应商人员"
    roles: ["SUPPLIER"]
```

**一条人员记录 + 一组匹配规则 = 自动推导出系统权限**。

## 4. 全生命周期管理

### 4.1 入职

```text
HR 在 H-UMDG 创建 DictPerson：
  person_name = "张三"
  department = "设备科"
  position = "工程师"
  person_type = "本院职工"
  status = "ACTIVE"

H-UMDG 自动执行规则匹配：
  ✅ H-MELC → 角色 [ENGINEER, DEPT_USER]
  ✅ H-UMDG → 角色 [DATA_STEWARD]
  
生成登录账号：
  username = 工号 或 手机号
  初始密码通过短信发送
  首次登录强制修改
```

**无需人工分配权限**，岗位决定了权限。

### 4.2 转岗

```text
张三从设备科调到财务科：
  department = "设备科" → "财务科"

H-UMDG 自动重新匹配规则：
  ❌ H-MELC 工程师权限 → 自动回收
  ✅ H-MELC 财务权限 → 自动开通
  ✅ 财务系统 → 自动开通
```

**无需人工回收旧权限、开通新权限**，转岗自动完成权限切换。

### 4.3 离职/退休

```text
张三离职：
  status = "ACTIVE" → "RESIGNED"

H-UMDG 自动执行：
  ✅ 该人员所有已签发的 JWT 立即失效
  ✅ 次日凌晨定时任务清理登录账号
  ✅ 审计日志记录：张三于 2026-06-04 离职
  ✅ 所有业务系统下一个 API 请求即拒绝
```

**无需逐个系统去禁用账号**，一个字段变更同步所有系统。

### 4.4 临时权限

```text
临时来院的外聘专家：
  person_type = "外聘专家"
  status = "ACTIVE"
  有效期 = "2026-06-04 ~ 2026-09-04"

规则匹配：
  ✅ 有效期内的 H-MELC 查看权限
  ❌ 有效期外 → 系统自动收回

JWT 的 exp 字段直接使用有效期的到期时间
```

## 5. JWT 载荷设计

```json
{
  "sub": "zhang_san",
  "person_id": "uuid-of-person",
  "person_name": "张三",
  "department_name": "设备科",
  "position": "工程师",
  "systems": {
    "H-MELC": {
      "roles": ["ENGINEER", "DEPT_USER"]
    },
    "H-UMDG": {
      "roles": ["DATA_STEWARD"]
    }
  },
  "iat": 1749000000,
  "exp": 1749086400
}
```

JWT 的载荷直接来自 `DictPerson` 的属性 + 规则匹配结果，**不查额外的表**。

## 6. 实现路径

### 第一步：DictPerson 扩展 + 规则配置

```python
# DictPerson 新增字段（迁移 0019）
class DictPerson(Base):
    # ... 现有字段不变
    login_account: Mapped[str | None] = mapped_column(String(100))  # 已有
    password_hash: Mapped[str | None] = mapped_column(String(255))  # 新增
    employment_status: Mapped[str] = mapped_column(  # 比 status 更细：在职/离职/退休/返聘
        String(20), default="ACTIVE"
    )
    onboard_date: Mapped[date | None] = mapped_column(Date)  # 入职日期
    offboard_date: Mapped[date | None] = mapped_column(Date)  # 离职日期
```

```yaml
# system_config 表中的配置项
access_rules:
  - rule_id: "rule-001"
    system_code: "H-MELC"
    match: {"position": "工程师", "department_name": "设备科"}
    roles: ["ENGINEER"]
  - rule_id: "rule-002"
    system_code: "H-MELC"
    match: {"person_type": "护士"}
    roles: ["DEPT_USER"]
```

### 第二步：认证逻辑改造

```python
def authenticate_person(username: str, password: str) -> str | None:
    """登录→获取人员→匹配规则→签发 JWT"""
    person = db.query(DictPerson).filter(
        login_account=username, 
        status="ACTIVE"
    ).first()
    if not person or not verify_password(password, person.password_hash):
        return None
    
    # 自动匹配规则，推导系统权限
    systems = access_rule_engine.match(person)
    # systems = {"H-MELC": {"roles": ["ENGINEER"]}, "H-UMDG": ...}
    
    return issue_jwt(person, systems)
```

```python
def access_rule_engine(person: DictPerson) -> dict:
    """根据人的属性匹配规则，返回 {system_code: {roles: [...]}}"""
    rules = load_access_rules()
    result = {}
    for rule in rules:
        if match_person(person, rule["match"]):
            sys_code = rule["system_code"]
            result.setdefault(sys_code, {"roles": []})
            result[sys_code]["roles"].extend(rule["roles"])
    return result
```

### 第三步：H-MELC 接入

H-MELC 去掉自己的用户表，JWT 中的 `systems.H-MELC.roles` 就是该用户在本系统的角色。角色映射到本地权限：

```python
# H-MELC 统一的 JWT 验证入口
def get_current_user(token: str) -> dict:
    payload = jwt.decode(token, JWT_SECRET_KEY)
    person_systems = payload.get("systems", {})
    if "H-MELC" not in person_systems:
        raise HTTPException(403, "无权访问本系统")
    return {
        "person_id": payload["person_id"],
        "username": payload["sub"],
        "roles": person_systems["H-MELC"]["roles"],
    }
```

## 7. 与传统 RBAC 的对比

| 维度 | 传统 RBAC（当前做法） | 主数据驱动（目标） |
|------|---------------------|-------------------|
| 权限来源 | 人工逐个分配角色 | 人员岗位自动推导 |
| 入职流程 | HR 录入 + IT 建账号 + 分配角色 | HR 录入即可 |
| 转岗 | 需人工回收旧权限、开通新权限 | 自动切换 |
| 离职 | 每系统逐个禁用 | 状态变"离职"即可 |
| 临时权限 | 手动设置到期时间 | 效期字段自动控制 |
| 审计追溯 | 分散在各系统 | 统一人员生命周期 |
| 权限可见性 | 需要逐个系统查询 | 查看 DictPerson 即知 |
| 规则变更 | 需要重新分配角色 | 改规则配置即可生效 |

## 8. 注意事项

1. **规则引擎复杂度**：初期用简单的键值对匹配（position + department），后续可扩展为表达式引擎。

2. **JWT 密钥管理**：所有业务系统共用 `JWT_SECRET_KEY`，密钥轮换需协调。建议使用 Vault 等密钥管理服务。

3. **离线容错**：JWT 本身带有效期（默认 8 小时），期间 H-UMDG 不可用不影响已有登录。新登录则等待 H-UMDG 恢复。

4. **历史兼容**：现有独立账号体系可通过"规则配置"逐步迁移——先实施双轨制，新规则优先，旧账号兜底。

5. **规则优先级**：同一人可能匹配多条规则，取角色并集。特殊规则（如黑名单）可优先级最高。
