# 主数据驱动的全院统一身份与权限管理方案

> **状态**：方案设计（迭代目标，非当前实现）
> **版本**：v0.1-draft
> **日期**：2026-06-04
> **提出人**：项目负责人
> **关联项目**：H-UMDG（主数据底座）、H-MELC（首个对接业务系统）

---

## 1. 背景与问题

### 1.1 现状

两个系统各自维护独立的用户账号体系：

| 系统 | 用户存储 | 鉴权方式 | 管理方式 |
|------|----------|----------|----------|
| H-UMDG | `identity.app_user` 表（新建） | JWT + bcrypt | 单独管理 |
| H-MELC | `identity.app_user` 表 | JWT + bcrypt | 单独管理 |
| 未来业务系统（HRP、SPD、HIS...） | 各自一套 | 各自实现 | 各自管理 |

### 1.2 问题

- 一个医生要登录 H-MELC 报修、SPD 查耗材、HIS 看患者——**需要三个账号**
- 人员离职后，H-UMDG 标记了"离职"，但 H-MELC 的 `identity.app_user` 仍为激活状态——**存在安全隐患**
- 院方管理者无法在一个地方看到"全院哪些人能登录哪些系统"
- 角色管理分散：每个系统各自定义"工程师""管理员"——**含义可能不一致**

---

## 2. 核心理念

> **人员是主数据，账号是派生属性，权限由数据中心统一下发。**

不再每个系统独立管理用户。H-UMDG 作为全院统一的人员主数据底座，**人员的基本信息、岗位、资质、系统账号、角色权限全部由 H-UMDG 统一维护**。业务系统（H-MELC、HRP、SPD、HIS 等）不再保有独立的用户表，而是通过标准 API 从 H-UMDG 获取当前人员信息并验证身份。

---

## 3. 数据模型扩展

### 3.1 现有人员主数据扩展

当前 H-UMDG 已有 `DictPerson` 表存储人员基础信息（工号、姓名、科室等）。在此基础上增加：

```sql
-- 岗位字典（已有的标准字典能力）
-- "主任医师"、"护士长"、"设备科工程师"、"财务科长"等

-- 系统账号（新增）
CREATE TABLE identity.platform_account (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    person_id UUID NOT NULL REFERENCES dict_person(id),
    -- ↑ 关联人员主数据，一个人员可以有多个系统账号
    username VARCHAR(64) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    is_active BOOLEAN NOT NULL DEFAULT true,
    last_login_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 跨系统角色映射（新增）
CREATE TABLE identity.system_role_mapping (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    role_code VARCHAR(64) NOT NULL,      -- H-UMDG 标准角色编码
    system_code VARCHAR(64) NOT NULL,     -- 目标系统：H-MELC / HRP / SPD ...
    target_role VARCHAR(128) NOT NULL,   -- 目标系统内的角色名
    UNIQUE(role_code, system_code)
);

-- 人员-系统-角色分配（新增）
CREATE TABLE identity.person_system_role (
    person_id UUID NOT NULL REFERENCES dict_person(id),
    system_code VARCHAR(64) NOT NULL,
    role_code VARCHAR(64) NOT NULL,       -- 引用标准角色字典
    granted_by UUID REFERENCES identity.platform_account(id),
    granted_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at TIMESTAMPTZ,               -- 可设置到期时间
    is_active BOOLEAN NOT NULL DEFAULT true,
    PRIMARY KEY (person_id, system_code, role_code)
);
```

### 3.2 核心原则

- **人员主数据是权威源**：一个人只在 H-UMDG 中有一条记录，通过 `person_id` 关联所有系统账号
- **账号绑定人员**：`platform_account` 的 `person_id` 指向 `DictPerson`，离职时只需在 H-UMDG 标记停用即可同步到所有系统
- **角色标准化**：H-UMDG 定义全院统一角色字典，映射到各系统的具体角色名

## 4. 架构流程

### 4.1 统一登录流程（OAuth2 风格）

```text
┌──────────┐   ① POST /auth/login       ┌──────────────┐
│          │ ──────────────────────────→ │              │
│  浏览器   │                             │  H-UMDG      │
│          │ ←────────────────────────── │  认证中心     │
└──────────┘   ② JWT (含 person_id,      │              │
                roles, 可访问系统列表)    └──────┬───────┘
                                                │
                        ③ 携 JWT 调用业务系统 API │
                                                ↓
                                      ┌─────────────────┐
                                      │ H-MELC / HRP /   │
                                      │ SPD / HIS ...    │
                                      │                  │
                                      │ ④ 验证 JWT 签名   │
                                      │ ⑤ 查阅本地缓存     │
                                      │    角色映射        │
                                      └─────────────────┘
```

**步骤说明**：

1. 用户在 H-UMDG 统一登录门户（或任意业务系统登录页）输入账号密码
2. H-UMDG 验证 `platform_account`，签发 JWT，载荷中包含：
   - `person_id`（人员主数据 ID）
   - `username` 和 `display_name`
   - `systems`：该人员被授权的系统编码列表（如 `["H-MELC", "SPD"]`)
   - `roles`：H-UMDG 标准角色编码
3. 业务系统收到 JWT 后验证签名（共用 `JWT_SECRET_KEY`），从 `person_system_role` 获取该人员在本系统的角色
4. 业务系统不查询自己的用户表——角色信息来自 H-UMDG

### 4.2 首次访问授权

```text
人员入职 → H-UMDG 创建 DictPerson
    ↓
HR 在 H-UMDG 中为该人员分配：
  - 系统访问权限（可登录哪些系统）
  - 角色（在各系统中是什么角色）
  - 有效期（可选）
    ↓
人员通过 H-UMDG 门户或任意系统登录 →
  看到授权的系统入口 →
  点击进入 H-MELC → H-MELC 从 JWT 解析角色 →
  呈现对应功能
```

### 4.3 离职与权限回收

```text
人员离职 → H-UMDG 标记 DictPerson.is_active = false
    ↓
下次该人员的 JWT 过期后 →
  无法刷新令牌（H-UMDG 拒绝登录）→
  所有系统同时失去访问能力
    ↓
如果需要立即可用：H-UMDG 发布
  "账号状态变更"事件到消息队列 →
  各业务系统订阅并缓存失效
```

## 5. 角色标准字典

H-UMDG 定义全院角色标准，映射到各业务系统的具体权限：

| H-UMDG 标准角色 | 描述 | H-MELC 映射 | SPD 映射 | 说明 |
|----------------|------|-------------|----------|------|
| `SYS_ADMIN` | 系统管理员 | `SYS_ADMIN` | `admin` | 全功能 |
| `DEVICE_ADMIN` | 设备管理员 | `DEVICE_ADMIN` | — | 设备全流程管理 |
| `DEPT_USER` | 科室用户 | `DEPT_USER` | `requisitioner` | 本科室操作 |
| `ENGINEER` | 工程师 | `ENGINEER` | — | 维修执行 |
| `AUDIT_ADMIN` | 审计管理员 | `AUDIT_ADMIN` | `auditor` | 审计日志 |
| `FINANCE_USER` | 财务用户 | `FINANCE_READ` | `finance` | 财务模块 |
| `SUPPLIER` | 供应商 | `SUPPLIER` | `vendor` | 供应商门户 |
| `DATA_STEWARD` | 数据治理员 | — | `data_admin` | 主数据维护 |
| `NURSE` | 护士 | `DEPT_USER` | — | 扫码报修等 |
| `DOCTOR` | 医生 | `DEPT_USER` | `clinical_user` | 临床操作 |

> 角色映射通过 `identity.system_role_mapping` 表维护，可在 H-UMDG 管理界面配置。

## 6. 对外接口设计

### 6.1 H-UMDG 统一认证接口

```yaml
POST /api/v1/auth/login
  Body: { username, password }
  Response: { access_token, expires_in, user: { person_id, name, systems: [...], roles: [...] } }

GET /api/v1/auth/me
  Header: Authorization: Bearer <JWT>
  Response: { person_id, username, display_name, systems, roles, permissions }

GET /api/v1/persons/{person_id}/systems
  → 返回该人员可访问的系统列表及角色

POST /api/v1/auth/token/validate
  → 内部接口，供业务系统验证 JWT 并获取用户最新角色

GET /api/v1/auth/system-roles?system_code=H-MELC
  → 返回某系统的角色映射字典
```

### 6.2 业务系统对接要求

业务系统只需做到两件事：

1. **验证 JWT 签名**：使用与 H-UMDG 相同的 `JWT_SECRET_KEY`
2. **从 JWT 读取角色**：从 `roles` 字段获取标准角色，映射到本地权限模型

## 7. 与组织/人员主数据的关系

H-UMDG 现有的组织与人员主数据能力已经覆盖：

| 当前能力 | 说明 |
|----------|------|
| `DictPerson` | 人员档案（工号、姓名、科室、岗位） |
| 科室层级 | `DictDepartment` 树形结构 |
| 人员-科室关系 | 主科室、兼职科室 |
| 岗位角色字典 | `staff_role_dict` |

在此基础上，统一身份方案只需扩展：

| 新增 | 说明 |
|------|------|
| `platform_account` | 系统登录账号（关联人员） |
| `person_system_role` | 人员-系统-角色分配 |
| `system_role_mapping` | 标准角色 → 系统角色映射 |
| 登录审计 | 记录登录事件到统一审计 |

## 8. 实施路径

### 阶段一：标准角色对齐（H-UMDG + H-MELC 先行）

```
工作量：约 1-2 周
内容：
1. H-UMDG 补充 platform_account / person_system_role 表
2. H-UMDG 补充系统角色映射管理页面
3. H-MELC auth 改为通过 JWT 中的 person_id 查询角色
4. seed_admin 脚本改为通过 H-UMDG 创建账号

交付：
- H-UMDG 作为认证中心：H-MELC 登录请求发往 H-UMDG
- 一个账号登录两个系统
```

### 阶段二：角色可视化

```
工作量：约 1 周
内容：
1. H-UMDG 管理端增加"系统权限总览"页面
2. 按人员、按系统、按角色三种视图
3. 权限到期预警

交付：
- 院长/信息科可在一处查看全院人员系统权限
- 离职流程自动回收所有系统权限
```

### 阶段三：扩展到其他系统

```
工作量：按对接系统数
内容：
1. HRP、SPD、HIS 等系统对接 H-UMDG 认证接口
2. 各系统角色映射配置

交付：
- 全院统一身份认证
```

## 9. 方案优势

| 维度 | 现状（各自为政） | 目标（主数据驱动） |
|------|----------------|-------------------|
| 账号管理 | 每系统一套用户表 | H-UMDG 统一管理 |
| 入职开通 | 每系统逐个创建 | H-UMDG 一次分配 |
| 离职回收 | 每系统逐个禁用 | H-UMDG 停用即同步 |
| 权限可见性 | 无法全局查看 | 系统权限总览 |
| 角色一致性 | 各系统定义不一 | 标准角色统一映射 |
| 审计追溯 | 每系统各自审计 | 统一登录审计 |
| 新人开发 | 每套新系统都要做鉴权 | 对接 H-UMDG 即可 |

## 10. 风险与注意事项

1. **H-UMDG 不可用影响登录**：所有系统的登录操作都依赖 H-UMDG。建议 H-UMDG 采用高可用部署（Patroni + 负载均衡），并在各业务系统保留 JWT 缓存（token 有效期内仍可工作）。

2. **旧系统兼容**：已上线的业务系统可能已有自己的用户表。过渡期可采用双轨制——H-UMDG 认证 + 本地用户表同步，逐步切换。

3. **JWT 密钥管理**：所有系统共用 `JWT_SECRET_KEY`，密钥轮换需要协调所有系统。建议使用独立密钥管理服务（Vault / KMS），各系统运行时读取。

4. **离线降级**：当 H-UMDG 不可用时，各业务系统应能使用本地缓存的 JWT 公钥验证已有 token，新登录则等待 H-UMDG 恢复。

5. **隐私合规**：统一身份意味着 H-UMDG 持有全院人员的系统访问数据，需要明确的隐私保护策略和数据访问权限控制。
